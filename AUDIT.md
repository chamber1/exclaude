# Технический аудит проекта exclaude

Дата: 19.11.2026. Аудит проведён по фактическому коду репозитория (коммит `a21d5c8`) и работающему окружению Docker.

## 1. Что представляет собой проект

| Компонент | Состояние на момент аудита |
|---|---|
| Фреймворк | Laravel 10.48.22, PHP 8.1.34 (образ `phpdockerio/php:8.1-fpm`, Ubuntu 22.04), Composer 2.11, PHPUnit 10.5 |
| Функции | Аутентификация `laravel/ui`; `/webcam` (камера, маска клоуна, снимки); `/parser` (звук и видео с YouTube через yt-dlp) |
| Инфраструктура | `docker-compose.yml`: `nginx`, `php_fpm`, `mysql`. Нет Redis, нет воркера очередей, нет планировщика |
| Драйверы | `QUEUE_CONNECTION=sync`, `CACHE_DRIVER=file`, `SESSION_DRIVER=file` |
| PHP-FPM | `pm = dynamic`, `pm.max_children = 5` |
| Тесты | Только `ExampleTest`; `phpunit.xml` указывает на рабочую БД |

Ключевой файл парсера — `app/Http/Controllers/ParserController.php` (≈380 строк): валидация, разбор URL, сборка команды yt-dlp, запуск процесса, разбор ошибок, логирование, выдача файлов и очистка находятся в одном контроллере.

## 2. Найденные проблемы

Критичность: **Критично** — эксплуатируется сейчас или блокирует цель B2C; **Высокая** — серьёзный риск безопасности или стабильности; **Средняя** — нужно исправить до production; **Низкая** — качество и сопровождение.

### 2.1. Архитектура и производительность

| # | Проблема | Где | Критичность | Решение |
|---|---|---|---|---|
| A1 | yt-dlp запускается **синхронно внутри HTTP-запроса** на время до 600 с. При `pm.max_children = 5` пять одновременных запросов `/parser` занимают все воркеры PHP-FPM, и весь сайт (вход, веб-камера) перестаёт отвечать. Это готовый DoS даже от одного пользователя с пятью вкладками | `ParserController::runYtDlp()`, `docker/nginx/default.conf` (`fastcgi_read_timeout 660s`) | **Критично** | Очередь Laravel на Redis и отдельный контейнер воркера. HTTP-запрос только создаёт задачу (≈50 мс). Таймаут nginx вернуть к стандартному |
| A2 | Число одновременных обработок ничем не ограничено: есть только `throttle:10,1` на пользователя, но нет ни лимита активных задач, ни глобального лимита | `routes/web.php` | **Высокая** | Лимит активных задач на владельца (под блокировкой Redis), глобальная ёмкость = число воркеров, отказ при переполнении очереди |
| A3 | Временные файлы удаляются «лениво» — при следующем запросе к парсеру (`removeStaleFiles`). Если запросов нет, неполученные видео до 2 ГБ остаются на диске бессрочно. Аварийно завершённые процессы оставляют `.part`-файлы | `ParserController::removeStaleFiles()` | **Высокая** | Каталог на каждую задачу, команда `downloads:cleanup` в Scheduler каждые 5 минут, очистка в `failed()` джоба |
| A4 | Состояние ссылок на видео хранится только в файловом кеше. Нет истории задач, статуса или прогресса; после перезапуска пользователь теряет результат | `Cache::put('parser:file:*')` | Средняя | Таблица `download_tasks` со статусами и сроками |
| A5 | Контроллер совмещает разбор URL, сборку команды, запуск процесса, разбор ошибок, логирование и выдачу файлов (нарушение SRP), поэтому его невозможно протестировать без реального YouTube | `ParserController` | Средняя | Выделить `UrlParser`, `YtDlp`, `DownloadService`, `DownloadJob`; контроллеры сделать тонкими |
| A6 | Файловые драйверы сессий и кеша не масштабируются на несколько контейнеров приложения и не дают атомарных блокировок между контейнерами | `.env` | Средняя | Redis для кеша, сессий, блокировок и очередей |
| A7 | Готовый видеофайл отдаётся через PHP (`BinaryFileResponse`), то есть воркер FPM занят всё время скачивания многогигабайтного файла | `ParserController::file()` | Низкая (после A1) | Ограничение размера и TTL; в перспективе `X-Accel-Redirect` (см. раздел 4) |

### 2.2. Безопасность

| # | Проблема | Где | Критичность | Решение |
|---|---|---|---|---|
| S1 | **SSRF сейчас не эксплуатируется**: из ссылки извлекается только 11-символьный ID, и в yt-dlp передаётся канонический `https://www.youtube.com/watch?v=<id>` после `--`. Но защиту обеспечивает лишь регулярное выражение; при добавлении второй платформы её легко потерять. yt-dlp не ограничен по экстракторам: если в команду попадёт произвольный URL, сработает `generic`-экстрактор, который скачает что угодно, включая `http://169.254.169.254/` и `http://mysql:3306/` | `extractVideoId()`, сборка команды | **Высокая** (превентивно) | Реестр поддерживаемых платформ (allowlist доменов); запрет IP-литералов, userinfo и нестандартных портов; DNS-проверка на private, reserved и link-local адреса; `--use-extractors youtube` (запрет `generic`); `--ignore-config`; `--no-playlist` |
| S2 | Конфиги yt-dlp читаются из `~/.config/yt-dlp`, `/etc/yt-dlp.conf` и рабочего каталога. Злоумышленник с правом записи в `HOME=/tmp` может подложить конфиг с `--exec` | вызов yt-dlp | Средняя | `--ignore-config` в каждом вызове, отдельный `HOME` |
| S3 | `chmod -R 777` на `storage` и `bootstrap` в образе | `docker/Dockerfile` | **Высокая** | Владелец `www-data`, права 775/664; воркер и планировщик запускаются от `www-data` |
| S4 | MySQL опубликован на `0.0.0.0:3306`. Root-пароль совпадает с паролем пользователя приложения (`MYSQL_ROOT_PASSWORD: ${DB_PASSWORD}`) | `docker-compose.yml` | **Высокая** | В dev привязка к `127.0.0.1`; в prod порт не публикуется; отдельная переменная `DB_ROOT_PASSWORD` |
| S5 | yt-dlp и Deno скачиваются при сборке как `latest` без проверки контрольной суммы (риск supply chain) | `docker/Dockerfile` | Средняя | Фиксированные версии через `ARG` и проверка SHA-256 (yt-dlp публикует `SHA2-256SUMS`) |
| S6 | `APP_DEBUG=true`: при любой 500-ошибке наружу уходят стек-трейсы, пути и SQL | `.env` | Высокая для prod | В `.env.production.example` `APP_DEBUG=false`; JSON-ошибки API без деталей |
| S7 | Нет лимита размера аудиофайла (`--max-filesize` только у видео). Длительность проверяется, размер — нет | `download()` | Низкая | Общий лимит размера на тариф и проверка размера после загрузки |
| S8 | Одноразовые ссылки на файлы — случайный UUID в кеше, без подписи и без привязки ко времени на уровне URL | `parser.file` | Низкая | Временная подписанная ссылка (`URL::temporarySignedRoute`) и проверка владельца |
| S9 | В `parser.log` пишется IP-адрес в открытом виде (персональные данные) | `ParserController::log()` | Низкая | HMAC-хеш IP (`client_hash`); сырой IP не хранится ни в БД, ни в журнале |
| S10 | `TrustProxies::$proxies = null`: за внешним балансировщиком или Cloudflare `request->ip()` будет адресом прокси, и лимиты гостей станут общими для всех | `TrustProxies` | Средняя для prod | `TRUSTED_PROXIES` из env |
| S11 | Нет заголовков безопасности (`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, HSTS), включён `server_tokens` | `docker/nginx/default.conf` | Средняя | Production-конфиг nginx |
| S12 | Внутренние сообщения yt-dlp наружу не выдаются (сопоставление через `errorMessage()`) — **в порядке** | — | — | Сохранить подход |
| S13 | Shell-инъекция **невозможна**: команда передаётся массивом аргументов (`Process::run([...])`), без конкатенации строк — **в порядке** | — | — | Сохранить |

### 2.5. Правовой риск (не технический, но критичный для B2C)

| # | Проблема | Критичность | Решение |
|---|---|---|---|
| L1 | Условия использования YouTube запрещают скачивание контента, кроме случаев, когда YouTube явно даёт такую возможность или есть разрешение правообладателя. Публичный сервис «скачай любое видео» несёт юридические риски (DMCA, блокировки) | **Критично** для коммерческого запуска | Политика лицензий в конфигурации: `DOWNLOADS_LICENSE_POLICY=creative_commons` разрешает только ролики под лицензией Creative Commons (поле `license` из метаданных yt-dlp). Обхода DRM, авторизации и платных ограничений нет и не будет. Решение о политике для production — за владельцем продукта; по умолчанию локально оставлено `any`, чтобы сохранить текущую функциональность |

## 3. План изменений (выполняется в этом порядке)

1. **Тестовая инфраструктура**: БД `laravel_test`, `phpunit.xml`. Без неё нельзя безопасно проверять остальные этапы.
2. **Доменный слой загрузок** (`app/Downloads/*`):
   - `Platform` / `UrlParser` / `NetworkGuard` — allowlist и защита от SSRF;
   - `YtDlp` — команды, прогресс, ошибки;
   - `DownloadService` — бизнес-правила;
   - `DownloadStatus` (enum), `DownloadTask` (модель и миграция), `users.plan`.
3. **Очередь**: `DownloadJob` (повторы, `failed()`, идемпотентность), Redis, `retry_after` больше таймаута джоба.
4. **HTTP**: `DownloadController` (inspect, create, status, file), `StoreDownloadRequest`, RateLimiter `downloads`, гостевой доступ. Синхронный `POST /parser` удаляется (причина — A1); страница `/parser` остаётся.
5. **UI**: страница `/parser` в той же разметке Bootstrap — проверка ссылки и метаданные, выбор из реально доступных качеств, прогресс, ссылка, ошибки, мобильная вёрстка.
6. **Очистка и мониторинг**: `downloads:cleanup`, `downloads:status`, heartbeat воркера и планировщика, `/up`, prune `failed_jobs`, Scheduler.
7. **Docker**: сервисы `app`, `queue-worker`, `scheduler`, `redis`; healthcheck; restart; лимиты ресурсов; убрать `chmod 777`; фиксированные версии с проверкой SHA-256.
8. **Production**: `docker-compose.prod.yml`, `docker/production/Dockerfile` (multi-stage), конфиг nginx с TLS, `.env.production.example`, `docs/DEPLOYMENT.md` (запуск, обновление, бэкап, восстановление, SSL).
9. **Обновление платформы**: `docs/UPGRADE.md` — план PHP 8.3 + Laravel 11/12 с оценкой рисков.
10. **Тесты** по всем пунктам этапа 9 и финальный прогон.

## 4. Решения, принятые сознательно

- **Laravel и PHP обновлены отдельным этапом**, после перевода загрузок на очередь и покрытия тестами: так причину любой поломки можно отнести к одному изменению. Структура приложения (Kernel-классы) сохранена, Laravel 13 её поддерживает. Подробности — `docs/UPGRADE.md`.
- **Новые Composer-зависимости не добавляются**: расширение `phpredis` уже есть в образе, `Process::fake()` и RateLimiter входят в Laravel 10.
- **Horizon не добавляется** (лишняя зависимость при одной очереди). Мониторинг — `downloads:status` и heartbeat.
- **`X-Accel-Redirect` для отдачи файлов** (пересмотрено в ходе работ, A7 закрыт полностью): PHP проверяет подпись и владельца, помечает задачу скачанной и передаёт отдачу nginx. Так как PHP не знает, когда nginx закончит отдачу, файл удаляет `downloads:cleanup` через `DownloadCleaner::DELIVERY_GRACE` (30 мин). Без nginx (пустой `DOWNLOADS_X_ACCEL_PREFIX`) файл отдаёт PHP и удаляет сразу.
- **Production-образ** — не отдельный `docker/production/Dockerfile`, а цели `prod` и `web` в общем `docker/Dockerfile` (multi-stage): одинаковая базовая часть для dev и prod.
